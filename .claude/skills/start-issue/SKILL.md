## 目的

実装に入る前に「何を作るか・何がすでにあるか・何を決める必要があるか」を揃える。
コードは書かない。計画と確認で1ターンを終える。

---

## 手順

### Step 0: イシューを読む

```bash
gh issue view <N>
```

タイトル・完成の条件・制約を把握する。設計書へのリンクがあればメモしておく。

### Step 1: 既存ブランチを確認する

```bash
git branch
```

関連しそうなブランチが見つかったら、main にないコミットがあるかを確認する：

```bash
git log main..<ブランチ名> --oneline
```

コミットが残っている場合は**ユーザーに見せてから**「新しく切るか、既存を使うか」を確認する。
コミットがなければ確認不要で次へ進む。

### Step 2: main に切り替えて pull する

```bash
git checkout main && git pull origin main
```

### Step 3: ブランチを切る

CLAUDE.md の命名規則に従う：

| 種別 | 形式 |
|------|------|
| イシューに紐づく機能 | `feature/issue-{N}-{説明}` |
| イシューに紐づかない直し | `chore/{説明}` |

```bash
git checkout -b feature/issue-<N>-<説明>
```

説明部分はイシューの内容を英小文字・ハイフン区切りで1〜3語にまとめる。

### Step 4: 情報収集（並行実行）

以下を同時に行う：

- `docs/` に設計書があれば読む（`docs/<機能名>.md` など）。なければイシューの完成条件を突き合わせ先にする
- `CLAUDE.md` を読んで App Conventions・命名規則・テストの決まりを把握する
- 差分に関係しそうなファイルを読む（`routes/web.php`・対応するコントローラ・モデル・Blade ビュー・config）

### Step 5: 計画を立てて確認を取り、承認後に実装に入る

まず「これを決めないと進められないこと」がある場合は先にすべて質問する。質問はまとめて1回で行う。

**変更が複数ファイルにまたがる・設計の判断が必要**な場合は plan モードに入る：

1. plan モードで変更対象と内容の表を作る
2. 表をユーザーに見せて承認をもらう
3. 承認が取れたら plan モードを抜けて実装に入る

**小さい件**（1〜2 ファイルの単純な変更、設計の判断が不要）は plan モードに入らない：

1. 「○○ファイルの△△を変えます」と一言伝える
2. 承認をもらってから着手する

---

## 制約

- コードは書かない。計画と確認で終わる
- Step 1 で既存ブランチにコミットが残っていたら、必ずユーザーに見せてから判断を仰ぐ
- 設計書が見つからなくても中断しない。イシューの完成条件を代わりに使う
- 質問は「これを決めないと進められない」ものだけに絞る。全部まとめて1回で聞く
